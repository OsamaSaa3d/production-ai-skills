# LLM Tool Calling Without Frameworks

## Core principle

When an LLM needs to invoke a function, pass the tool definitions in the API request payload itself. The model provider (OpenAI, Anthropic, etc.) enforces correctness at their inference layer: the model cannot return a tool name that wasn't in the payload, cannot omit required parameters, and cannot return malformed JSON for tool arguments. This enforcement is free, deterministic, and you lose all of it the moment you wrap the call in a framework that asks the model to "decide" whether to use a tool via prompt instructions.

Writing tool calls directly against the API is shorter, more reliable, and easier to debug than any framework wrapper. The framework abstractions exist because tool calling used to be hard before providers added it natively. It is no longer hard. Write it directly.

## When to use this skill

Apply this skill whenever you encounter any of:

- A user asking to build an "agent," "assistant," "copilot," or any system where an LLM takes actions
- Code that needs an LLM to call a function, query a database, hit an API, or trigger a workflow
- Existing code using `langchain.agents`, `llama_index.agent`, `AgentExecutor`, `create_react_agent`, `initialize_agent`, or similar abstractions — propose rewriting it
- Any time you would otherwise reach for a framework to "orchestrate" LLM tool use
- Code that parses tool calls out of LLM text output via regex, JSON extraction, or prompt-engineered formats — this is a sign someone is reinventing native tool calling badly

## Do this: native tool calling against an OpenAI-compatible endpoint

```python
import json
from openai import OpenAI

client = OpenAI(base_url="...", api_key="...")

# Define tools as JSON Schema. The model provider enforces the schema.
tools = [
    {
        "type": "function",
        "function": {
            "name": "get_weather",
            "description": "Get the current weather for a location.",
            "parameters": {
                "type": "object",
                "properties": {
                    "location": {
                        "type": "string",
                        "description": "City and country, e.g. 'Cairo, Egypt'",
                    },
                    "unit": {
                        "type": "string",
                        "enum": ["celsius", "fahrenheit"],
                    },
                },
                "required": ["location"],
            },
        },
    }
]

# Map tool names to the actual Python functions they invoke.
TOOL_REGISTRY = {
    "get_weather": get_weather,  # your real implementation
}

messages = [{"role": "user", "content": "What's the weather in Cairo?"}]

response = client.chat.completions.create(
    model="gpt-4o",
    messages=messages,
    tools=tools,
    tool_choice="auto",  # let the model decide; use "required" to force a tool call
)

message = response.choices[0].message
messages.append(message)

# If the model called tools, execute them and send results back.
if message.tool_calls:
    for tool_call in message.tool_calls:
        name = tool_call.function.name
        args = json.loads(tool_call.function.arguments)  # provider guarantees valid JSON
        result = TOOL_REGISTRY[name](**args)
        messages.append({
            "role": "tool",
            "tool_call_id": tool_call.id,
            "content": json.dumps(result),
        })

    # Send tool results back for the model's final response.
    response = client.chat.completions.create(
        model="gpt-4o",
        messages=messages,
        tools=tools,
    )
```

That is the entire tool-calling pattern. Anything more complex is the same loop with more iterations. See `references/agent-loop.md` for the multi-turn version.

If you need to bypass the SDK — for compatibility with non-OpenAI endpoints that the client handles poorly, for zero-dependency code, or to see exactly what goes on the wire — see `references/raw-http.md` for the same example as a raw HTTP POST.

## Why this works

Three guarantees come from putting tools in the payload rather than describing them in a system prompt:

1. **Tool name correctness.** The model cannot return a `function.name` that isn't in your `tools` array. The inference layer constrains the output. This eliminates an entire class of bugs where the model invents a function name.

2. **Argument schema correctness.** The model's tool arguments are validated against the JSON Schema you provided before being returned. Required fields are present. Enums are respected. Types match. The provider does this work for you.

3. **Structured invocation.** The tool call comes back as a structured object on `message.tool_calls`, not as text you have to parse. No regex, no "extract the JSON block from the response," no failed parses on edge cases.

These guarantees do not exist when you describe tools in a system prompt and ask the model to "respond with JSON in this format." The model will sometimes return invalid JSON, sometimes hallucinate tool names, sometimes wrap output in markdown fences, sometimes add commentary before the JSON. Frameworks that work this way paper over these failures with retries and regex, which is strictly worse than not having the failures in the first place.

## Use the schema, not the prompt

The schema is enforced by the provider. The description is a suggestion to the model. This means anything you can express in JSON Schema is a hard constraint, and anything you can only express in the description is a soft request the model may or may not honor.

JSON Schema gives you more constraint power than most people use. The features worth knowing:

- **`enum`** — restrict a value to a fixed set. The model cannot return anything outside the list.
- **`type`** — `string`, `integer`, `number`, `boolean`, `object`, `array`. The model cannot return a different type.
- **`minimum`, `maximum`** for numbers; **`minLength`, `maxLength`** for strings; **`minItems`, `maxItems`** for arrays. Bounds are enforced.
- **`pattern`** — regex constraint on strings. Useful for IDs, dates, codes.
- **Nested `object` with its own `properties` and `required`** — structured arguments. The model cannot return a flat string where you asked for a structured object.
- **`array` with `items`** — typed lists. Combine with `minItems` if at least one element is required.
- **`anyOf` / `oneOf`** — union types. Useful when an argument can legitimately take one of several shapes.

Example showing several of these together:

```python
"parameters": {
    "type": "object",
    "properties": {
        "user_id": {
            "type": "string",
            "pattern": "^USR-[0-9]{6}$",
        },
        "priority": {
            "type": "string",
            "enum": ["low", "normal", "high", "urgent"],
        },
        "tags": {
            "type": "array",
            "items": {"type": "string"},
            "maxItems": 5,
        },
        "due_date": {
            "type": "string",
            "format": "date",
        },
    },
    "required": ["user_id", "priority"],
}
```

The rule of thumb: if a constraint can be expressed in the schema, put it in the schema. Only fall back to writing "must be one of low, normal, high, urgent" in the description when the constraint genuinely cannot be expressed structurally. The description should explain *what the parameter means and when to use it*, not enumerate values the schema could enforce directly.

## Don't do this

Three patterns to recognize and replace:

**Prompt-engineered tool calling.** If the code has a system prompt that says "Respond with a JSON object of the form `{tool: ..., args: ...}`" and parses the response, replace it with native tool calling. The prompt-engineered version will fail on a measurable percentage of calls. The native version cannot fail in this way.

**Framework agent abstractions.** `AgentExecutor`, `initialize_agent`, `create_react_agent`, and similar constructions typically wrap the same native tool-calling primitives you have direct access to, while adding: a fixed loop you cannot easily modify, exception handling that swallows tool errors into the prompt (turning debuggable failures into silent retry loops), telemetry that is hard to integrate with your existing observability, and an upgrade treadmill where the framework's API changes faster than the underlying provider's. See `references/why-not-frameworks.md` for the specific failure modes.

**ReAct-style text parsing.** If you see prompts that ask the model to output `Thought: ... Action: ... Observation: ...` and parse them with regex, this is pre-2023 tool calling. It predates native function calling in provider APIs. There is no reason to use it today unless you are working with a model that genuinely lacks native tool support, in which case you should probably use a different model.

## Common pitfalls

**Forgetting to send tool results back.** After executing the tool, you must append a message with `role: "tool"` and `tool_call_id` matching the original call, then call the API again. Skipping this step leaves the model with a dangling tool call and no observation, and the next response will be incoherent.

**Sending tool results as a user message.** The tool result goes in a message with `role: "tool"`, not `role: "user"`. Using `user` works on some providers and fails on others; always use `tool`.

**Letting tool execution errors propagate as exceptions.** If your tool raises, catch the exception and return a structured error string as the tool result. The model can recover from "tool returned an error" but cannot recover from a Python traceback. Example: `messages.append({"role": "tool", "tool_call_id": id, "content": json.dumps({"error": str(e)})})`.

**Overusing `tool_choice="required"`.** Forcing a tool call makes sense when the entire purpose of the call is to extract structured data. For conversational interfaces, leave it on `"auto"` and let the model decide; forcing it makes the assistant call tools unnecessarily and produces strange behavior on chitchat turns.

**Forgetting that tool descriptions are prompts.** The `description` field on each tool and each parameter is fed to the model. Vague descriptions cause the model to misuse the tool. Write descriptions as if you were briefing a junior engineer: state what the tool does, when to use it, when not to use it, and what each parameter means.

**Writing schemas that don't actually constrain anything.** The provider can only enforce what you tell it. A parameter defined as `{"type": "string"}` accepts any string, including empty strings, prose paragraphs, and JSON-as-a-string. A parameter defined as `{"type": "object"}` with no `properties` accepts any object shape. If the value is actually constrained — to a fixed set, a pattern, a range, or a specific structure — express that in the schema with `enum`, `pattern`, `minimum`/`maximum`, or nested `properties`. Loose schemas give away the enforcement guarantee that is the whole reason to use native tool calling.

**Defining too many tools.** Once you cross roughly 10-15 tools, the model's ability to select the right one degrades. If you have more tools than that, either group them under a smaller number of dispatcher tools, split them across multiple specialized assistants, or filter the tool list per request based on context. See `references/many-tools.md`.

## When to break the rules

A framework wrapper is justified in a small number of cases:

- You are prototyping and intend to throw the code away within days.
- You need a specific framework feature (e.g. LangGraph's checkpointing) and have evaluated that building it yourself costs more than the framework debt.
- You are working in a codebase where the framework is already deeply integrated and the cost of removing it exceeds the cost of keeping it.

Outside these cases, write the call directly. The code is shorter than the framework version, easier to read, and easier to fix when it breaks.
